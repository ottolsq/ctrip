# 目标与范围

## 问题

功能已覆盖 P0–P3，但「为什么做、做到哪、不做什么」散在 README 与 `docs/` 的计划里：README 承载技术栈与亮点，计划按日期堆积。想知道边界的人（答辩评委、后续接手的自己）只能通读全部。

## 用户

- 开发者本人：单人毕业设计，需要一条能在答辩现场完整演示的链路
- 平台用户：年轻人，发布/浏览攻略、创建行程、购买盲盒
- 运营角色：`ADMIN` / `CONTENT_OPERATOR`，通过后台管理内容、盲盒与订单

## 目标

- P0–P3 功能闭环可演示：内容社区、行程规划、盲盒（含秒杀）、后台管理
- 关键链路有可复现证据：API E2E 脚本、库存压测、Redis↔MySQL 每小时对账
- 技术债只登记不扩散，清单在 `ctrip-backend/docs/other/technical_debt.md`

## 非目标

- 不接真实支付通道：盲盒支付走内部回调模拟，无第三方网关 SDK
- 不做容器编排与多机房：部署为 WSL 内 jar + nginx
- 不做原生移动端、多租户、国际化

## 成功标准

| 指标 | 目标 | 怎么测 |
|---|---|---|
| 功能闭环 | P0–P3 全部可演示 | 任务书逐项走查 |
| 接口可用 | E2E 脚本全绿 | `ctrip-backend/scripts/run_all_e2e.py` |
| 不超卖 | 秒杀库存一致 | `stress_blindbox.py` + 对账日志 |

## 约束

- Windows 11 + WSL2（Ubuntu 24.04），JDK 25 / Node 26
- 依赖本地 MySQL / Redis / RabbitMQ 全部可用
- AI 方案生成依赖阿里云 DashScope，无网即不可用

## 开放问题

- 答辩后是否继续演进：决定 `FLASH-*` / `OPS-*` 技术债何时处理
