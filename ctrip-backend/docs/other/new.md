## 项目介绍

面向年轻人的社交化旅游 Web 平台，采用"内容种草 → 智能规划 → 盲盒探索"业务闭环，包含用户认证、内容社区、行程管理、AI 盲盒四大模块。**核心创新：** 用户购买盲盒后由通义千问 AI 生成个性化旅行方案，支持一键导入行程规划。

## 项目亮点

### 1. 企业级 JWT 双 Token 认证体系

Access Token(15min) + Refresh Token(15天) 轮换机制，刷新时吊销旧 Token 并颁发新 Token 防重放攻击；Refresh Token 仅存 SHA-256 哈希（原始值不落库），BCrypt 加密(强度12)，账号不存在与密码错误返回相同错误信息防用户枚举，Bucket4j 令牌桶按 IP 限流防暴力破解，三级角色权限控制(USER/ADMIN/CONTENT_OPERATOR)。

**面试要点：** JWT 无状态登出（Refresh Token 吊销 + Access Token 自然过期）、Token 哈希存储防泄露、防用户枚举攻击。

---

### 2. 高并发秒杀——三级方案演进 ⭐⭐⭐⭐⭐

| 方案 | 技术 | QPS | 响应时间 | 实现复杂度 | 状态 |
|------|------|-----|---------|-----------|------|
| 第 1 级 | Redisson 分布式锁 + MySQL 乐观锁 | < 100 | ~50ms | 低 | ✅ 已实现（日常购买） |
| 第 2 级 | **Redis Lua 脚本原子预扣 + MQ 异步削峰** | 1,000+ | ~5ms | 中 | ✅ 已实现（限时抢购） |
| 第 3 级 | 完整秒杀链路（网关限流 + Lua + MQ + 对账） | 10,000+ | ~2ms | 高 | 📋 设计文档保留 |

**第 2 级核心实现：**
- Lua 脚本内完成"查询库存 → SISMEMBER 防重复 → DECR 扣减 → SADD 记录用户"四步原子操作，返回码 1=成功 / 0=售罄 / -1=重复购买
- 秒杀成功后 RabbitMQ 异步发送订单消息削峰，不阻塞用户请求
- 消费端 Redis SETNX 幂等检查 + MySQL 乐观锁最终扣库存，双重保障

**配套机制：** 库存预热、@Scheduled 每小时 Redis↔MySQL 对账、撤销订单自动回补库存。

**面试要点：** Lua 为什么原子（Redis 单线程）、Redis 扣了但 MQ 失败怎么办（MQ 重试 + INCR 回补 + 对账修正）、方案演进理由（按并发量选方案，不过度设计）。

---

### 3. 热点缓存——三层穿透防护 ⭐⭐⭐⭐⭐

```
请求 → 布隆过滤器(判断key是否存在)
         ├── 不存在 → 直接返回 404（不查DB）       ← 第1层
         └── 可能存在 → Redis GET
                         ├── 命中 → 返回 (< 5ms)    ← 第2层
                         ├── 未命中 + DB有 → 写缓存返回
                         └── 未命中 + DB也无 → 缓存空值 ← 第3层
```

| 层 | 策略 | 实现 | 效果 |
|----|------|------|------|
| 第 1 层 | 布隆过滤器 | Redisson RBloomFilter，启动时加载全部有效 ID | 拦截不存在的 ID，"一定不存在"保证不穿透 |
| 第 2 层 | 空值缓存 | DB 查不到时写 `{"__null__":true}`，TTL 1min | 防同一无效 ID 反复击穿 DB |
| 第 3 层 | 参数校验 | `@Validated` + `id > 0` 约束 | 拦截 -1、null 等非法输入 |

**防雪崩：** TTL 随机偏移 ±10%（24h → 实际过期在 21.6h~26.4h 随机分散，避免大量 key 同时过期）。
**一致性：** Cache-Aside 模式，写操作主动删缓存（精准删详情 key + 通配删列表 key），不追求强一致，容忍短暂不一致。

**面试要点：** 穿透/击穿/雪崩三者的区别与解法、布隆过滤器误判处理（"不存在"一定对，"存在"可能误判）、缓存一致性取舍。

---

### 4. RabbitMQ 异步事件驱动 + 开盒重构 ⭐⭐⭐⭐

**事件体系：** 4 个 Topic Exchange + 10 个 Queue，覆盖订单状态变更、盲盒开盒、用户行为、内容审核四大事件域。

**核心改造——同步开盒 → 异步开盒：**
```
改造前（阻塞）：POST /open → 获取分布式锁 → 更新状态 → 
  同步调用 AI（5-20s 阻塞！）→ 保存结果 → 释放锁 → 返回

改造后（异步）：POST /open → 获取分布式锁 → 状态 → PROCESSING → 
  发送 MQ 消息 → 立即返回（毫秒级）
     ↓ (异步)
  MQ Consumer → 调用 AI 生成方案 → 保存结果 → 状态 → OPENED
  前端轮询 GET /result 获取（后续可升级 WebSocket 推送）
```

**订单状态机：** PENDING → PAID → PROCESSING → OPENED / CANCELLED，含幂等处理（已支付再支付、已开盒再开盒直接返回已有结果）和非法操作拦截（已支付不可取消、待支付不可开盒）。

**可靠性保障：**
| 层 | 机制 |
|----|------|
| Broker 层 | 消息/队列/Exchange 持久化 `durable=true` |
| 消费层 | 手动 ACK（处理成功才确认） |
| 重试层 | 指数退避 3 次（1s→5s→30s）+ 死信队列 |
| 幂等层 | Redis SETNX 检查 eventId（防重复消费） |
| 降级层 | MQ 故障时降级为日志，不阻塞主流程 |

**面试要点：** 为什么异步改造（用户体验 + 可靠性）、消息不丢失三保险（持久化 + 手动ACK + 死信）、重复消费去重（SETNX）。
